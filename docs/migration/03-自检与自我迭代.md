# 03 · 自检与自我迭代（Self-check & Self-iteration）

> 这份文档回答：**这套工作流怎样发现自己的问题、哪些问题它能自己修、哪些必须人批。**
> 迁移到新平台时，这一层是"它是否可信"的关键，也是**最值得照搬**的部分。

---

## 1. 为什么要分「自检」和「自我迭代」

| | 自检（Self-check） | 自我迭代（Self-iteration） |
|---|---|---|
| 对象 | **数据与产物的正确性** | **规则本身**（关键词、配额、渠道） |
| 例子 | JSON 能解析？id 唯一？digest 是子集？ | `dit` 这个词太宽，要不要删？ |
| 产出 | 报告 + 退出码 | 提案（proposal）+ 少量自动修改 |
| 谁能改 | 不改任何东西，只报告 | 一类可自动，其余需人批 |

**自检回答"数据是不是坏的"；自我迭代回答"规则是不是该改"。**
两者混在一起会出事：让系统自动重写评分逻辑，风险远大于收益。

## 2. 自检层：`scripts/selfcheck.py`

### 2.1 断言清单（实测 18 项通过）

| 组 | 断言 |
|---|---|
| `check_all_json` | 所有 JSON 可解析 |
| `check_required` | 必填文件存在且非空（manifest / items/index / digest / sources / taxonomy…） |
| `check_index` | id 唯一；`category` 在 taxonomy 内；`relevanceScore` 是数字；摘要覆盖率；未知域名占比；`manifest.totalItems` 与索引一致；`digest.items` 是索引子集（否则报 orphans） |
| `check_runs` | 有运行历史；最近一次运行状态；**距今小时数**（>26h 警告"18:00 的排期可能失败"）；**连续 3 轮以上失败的渠道**（升级为告警） |
| `check_proposals` | 提案文件数与待评审队列 |
| `check_collection_quality` | ①**分类集中度**（某类 >30% 警告）②**相关度区分度**（≥70 占比 >60% 说明打分不再有区分力）③**摘要覆盖率** ④**深读覆盖率** ⑤**反馈回路状态** |
| `check_redundancy` | ①**硬重复**（重复 id / 共用 URL）②**未分类占比**（≥15% 警告，≥5% 提示）③**标题套式重复**（同类目内 ≥10% 的标题以相同词开头）④**分类内主题同质化**（相似配对 ≥10%） |

`check_redundancy` 直接复用 `analyze_redundancy.build_report()`，所以**每日门禁与手动报告的判定永远不会不一致** —— 这是一个刻意的设计：两处各写一套阈值，早晚会互相矛盾。

### 2.2 退出码语义（**必须照搬**）

```
0  全部通过
2  有告警（部分渠道失败、或有质量告警）  ← 常见且正常
1  有错误（数据损坏）
```

`run-daily.ps1` 把 `2` 直接透传到任务计划程序，所以任务历史里看到 `2` **不是故障**。

### 2.3 为什么要 `check_collection_quality`

只验证"文件一致"是不够的：**一个完全自洽的语料仍然可能毫无用处**。
实测遇到过的三种退化，全都是文件一致但质量崩了：

1. `agent` 类占到 24% —— 某个话多的渠道/宽泛关键词在灌语料
2. 96% 的条目都 ≥50 分 —— 打分不再有区分力，排序失去意义
3. 大量条目只有标题 —— 无法深读，卡片等于书签

这三条现在都有断言。

### 2.4 `check_knowledge_quality`：库里到底积累了什么

`check_collection_quality` 证明的是**文件自洽**（id 唯一、分类均衡、摘要齐全）。
一个完全自洽的语料仍然可能是**错的语料**：全是"刚发布但会过期"的资讯，和一堆
与目标方向无关的求职帖，而用户真正在学的东西（算法推导、目标方向的面经、八股笔记、
手撕题）永远不增长。

这一组断言的每个数字都来自 `scripts/knowledge_quality.py`（采集器、深读规划器、
清理器共用的同一份判断），所以它不可能与实际入库/入队的内容不一致：

| 断言 | 阈值 | 不过说明什么 |
|---|---|---|
| 资讯（`kind=news`）占比 | ≤ 5% | 趋势类关键词过宽，正在收会过期的东西 |
| 低材料性占比 | ≤ 30% | 有一批没有实质内容的卡片，去跑 `prune_items.py --show` |
| 材料性中位数 | ≥ 0.35 | 一半以上的卡片知识含量偏低 |
| 四个目标方向的知识型条目 | 各 ≥ 15 | 某方向被资讯挤占 |
| 面经 / 手撕笔试题 / 知识点八股 | 各 ≥ 8 | **采集盲区**：实测这三类长期只有 `1` 条手撕题，而这是用户点名要积累的资产 |
| 方向不贴合的求职内容占比 | ≤ 10% | 来源关键词过宽（例如"面经"把后端面经一起收进来） |
| **论文方向纯度** | **应全为 0** | 库里出现 `technical_reject()` 判不过的论文（非 CS 学科 / 单一领域应用 / 只靠泛化 AI 词命中）—— 说明采集闸门没生效 |
| **论文分类饱和** | **不超上限** | 某方向的论文堆到超过 `maxPapersPerCategory[Target]`，冗余正在淹没关键内容 |

> 后两条是 2026-10-03 加的。前一条回答"论文是不是方向内的"，后一条回答"是不是太多了"。
> 两者都不是**错误**（数据仍然自洽），但都会让工作台一天比一天难用，所以放进每日自检。
> 判定全部复用 `scripts/knowledge_quality.py`，所以采集、清理、自检三处的结论必然一致。

> 阈值刻意设成"健康语料能过"：**一个永远失败的守卫等于没有守卫**。
> 这些是真实缺口时才报警，并在 `proposals/*.json` 里给出可执行的下一步。
>
> 另有一类"为空是设计如此"的分类**不再进入待办**：`unclassified`（`dropUnclassified`
> 开启时必须为空）、`paper` / `trend`（泛化兜底桶，方向内的论文会被四个目标分类接走）。
> 只有**有实质意义的方向分类**为空才值得人看（例如 `exam` 长期为空 = 采集盲区）。

## 3. 自我迭代：提案（Proposal）机制

### 3.1 三个来源

| 来源 | 文件 | 特点 |
|---|---|---|
| **确定性层** | `collect.py` 的 `write_proposals()` | 无需 LLM。渠道健康、失效关键词、未知域名、待办队列 |
| **知识质量层** | 同上（`knowledgeQuality` / `channelQualityProposals` / `kindGapProposals`） | 无需 LLM。把"积累缺口"直接变成**关键词提案**（唯一可自动生效的一类）与渠道降级建议（需人工批准） |
| **Agent 层** | `daily-agent.md` 第 4 节 | 需要 LLM。误分类证据、taxonomy 调整建议、渠道处置建议 |

知识质量层的意义：LLM 深读层需要凭据、可能被跳过，但"库里该积累什么都没积累起来"
必须**每一轮都被度量并产出可执行提案**。它把
「手撕/笔试题只有 1 条」→「给 `coding` 补 `题解 / hot 100 / 手撕代码` 等关键词」
这条链路做成确定性的，不依赖任何模型。

Agent 层会把**能复核的证据**（条目 id）写进 `reason`，这一点很重要：
「3 条误分类，id 分别是 …」比「感觉分类不准」有用得多。

### 3.2 提案类型

| 键 | 内容 | 谁能改 |
|---|---|---|
| `channelHealth[]` | 每渠道 status / streak / evidence / suggestedAction / escalate | 人工 |
| `keywordProposals[]` | `{category, add[], remove[], reason}` | **可自动**（有护栏） |
| `taxonomyProposals[]` | `{action: add\|split\|merge\|reweight, category, reason, proposedKeywords}` | 人工 |
| `newChannelProposals[]` | 人工导入 ≥5 次的未知域名 → 候选渠道 | 人工 |
| `noiseReport` | `overBroadKeywords` / `underCoveredCategories` / `unknownHosts` | 参考 |
| `humanReviewQueue[]` | 需要人确认的事项（自由文本，逐条说清确认什么） | 人工 |

### 3.3 `reviewPolicy`：谁能自动生效（**契约级，不要放宽**）

```json
{
  "autoApplicable": ["单个关键词权重 ≤10% 的微调"],
  "requiresHumanApproval": [
    "分类增删改名", "渠道增删与升降级", "评分公式与权重",
    "去重阈值", "blocklist", "robots.txt 状态变化"
  ]
}
```

**为什么只有关键词微调可以自动**：
- 影响面小、可回滚、下一轮打分立刻体现效果
- 判定依据是**客观的**（命中率、误分类样本 id）
- 改错了不会让语料消失，只是分类偏一点

**为什么其余必须人批**：这些改动会**改变系统对"什么重要"的定义**。
自动重写评分公式等于让系统自己给自己定标准，一旦偏了没有任何纠错锚点。

## 4. 唯一的自动生效通道：`scripts/tune_keywords.py`

```
读 proposals/latest.json 的 keywordProposals
  → 逐条施加硬性护栏
  → 通过的写入 config/collector.config.json
  → 追加审计记录 web/data/proposals/keyword-tune-log.jsonl
```

### 4.1 硬性护栏（任何一条不过就丢弃该条改动）

| 护栏 | 规则 | 防的是什么 |
|---|---|---|
| 形状 | 长度 3–30、小写、不含正则元字符 | 注入脏词、把分类器搞崩 |
| 停用词 | 拒绝 `review` / `theory` / `architecture` / `state of` 等通用词 | **实测**：`theory` 把比亚迪充电站带进 foundation |
| 跨类共用 | 不得出现在其它分类的关键词表里 | 两个分类互相抢条目 |
| 核心词保护 | `PROTECTED` 表里的词不可删（如 `ppo` / `attention` / `多模态`） | 删掉分类的身份词 |
| 单类上限 | 每轮每类最多 5 个 | 一次翻转整个分类 |
| 全局上限 | 每轮最多 12 个 | 一次改坏整张分类表 |

### 4.2 审计记录（可回滚）

```jsonc
{"at":"2026-10-02T02:06:08+08:00","appliedBy":"tune_keywords.py (auto-minor)",
 "changes":[{"category":"generative","add":["diffusion transformer"],"remove":["dit"],
             "reason":"dit 为子串匹配，把教育评估与精神病学综述带进 generative（证据 657ce65b…、7a6ec1f5…）"}],
 "rejected":[{"category":"rl","keyword":"ppo","reason":"protected core keyword"}]}
```

**这条记录是实测产物**，说明两件事同时成立：
1. 它确实动手删了该删的（`dit` / `intern` / `基础`）
2. 它确实拒绝了不该动的（`ppo` / `attention` 受保护）

回滚方式：从日志里取 `changes`，把 `add` 移除、`remove` 从 `keywordRemove` 里去掉即可。

### 4.3 关键词的两个通道（配置结构）

```jsonc
// config/collector.config.json
"categories": {
  "generative": {
    "keywords": ["diffusion transformer"],        // 追加
    "keywordRemove": ["dit"]                       // 退役内置词
  }
}
```

> 为什么需要 `keywordRemove`：默认词表在 `collect.py` 的 `DEFAULT_CATEGORIES`（代码内），
> 配置只能**追加**。没有删除通道，一个被证明过宽的词就永远退役不了。

## 5. 反馈回路：让规则跟着读者走

这是"自我迭代"里最容易被忽略、但对**个人**工作台最有价值的一环。

```
浏览器 localStorage（收藏 / 在学习 / 已掌握）
  ↓ 「写出学习信号」按钮（进度与统计页）
web/data/feedback.json         ← 只含 item id 与类目名，无个人内容
  ↓ collect.py 读取
类目 +最多 8 分 / 渠道 +最多 4 分（有上限，不会淹没其它方向）
  ↓ plan_deep_read.py 读取
深读配额向这些方向倾斜（catw +最多 0.1）
```

**关键细节：过期加分会被重建。** 加分是烘进 `relevanceScore` 的，
所以删掉 `feedback.json` 后如果不处理，条目会永远保留那次加分。
`collect.py` 每次启动都会：`base = score - 旧bonus`，再按当前信号重算。
实测：删掉 feedback.json 后 5 条残留加分被正确回退，且**幂等**（第二次运行不再改动）。

## 6. 产物守卫：`scripts/run_guards.py`

| 守卫 | 性质 | 为什么 |
|---|---|---|
| `check-formulas.mjs` | **门禁** —— 失败则**拒绝发布** | 「公式剖析」页整体是一个模板字符串，一条畸形 LaTeX 会让**整页空白**。Agent 每晚无人值守新增公式，坏字符串可能在夜里出现 |
| `tex-audit.mjs` | **门禁** —— 失败则**拒绝发布** | 渲染器对不认识的命令会**降级显示成原始 LaTeX**（刻意的：让拼写错误可见）。所以一条公式可以"不抛异常但显示 `\!` / `\odot`"。实测一次有 **38/155** 条泄漏命令，读者看到的就是"数学没渲染出来" |
| `verify-text-stacking.mjs` | 体检 | `display: grid` + `place-items: center` 会把**中文字符逐字变成网格项**，两字标签就竖排（"公"压在"开"上），表格看起来像错位。不溢出、不报错、DOM 正常，只能靠实测发现 |
| `verify-collapse.mjs` | 体检 | 作者样式（`.formula-body { display: grid }`）会**压过 UA 样式的 `[hidden] { display: none }`**，于是折叠控件设了属性、更新了 `aria-expanded`、DOM 状态全对，**屏幕上却毫无变化** —— 按钮看起来完全失效 |
| `audit-layout.mjs` | 体检（仅记录） | 有内容被 `overflow` 裁掉，不阻断 |

**这三个 UI 守卫都是真实故障的产物，而且都躲过了所有静态检查**：它们既不溢出也不报错，标记合法、DOM 状态正确。只有真的驱动浏览器才会暴露。它们默认自带静态服务器（`serve-dist.mjs`），因为一个因为"连不上服务器"而失败的守卫，只会训练你忽略它。

**门禁的发布语义**：公式失败 → `siteOk = false` → 跳过 WorkBuddy 发布交接。
**线上保留昨天那份正常站点。宁可旧，不可坏。**

### 6.1 关于布局审计的诚实说明

`audit-layout.mjs` 会报告一些"窄处文字被裁"的情况，其中一部分是**误报**：
`inline-flex` 元素的 `scrollWidth` 会虚报（例如统计条 `14/24` 被压扁）。
工具已做严重度过滤（`<8px` 忽略、`ellipsis`/`line-clamp` 视为有意截断），
但**看到"大量溢出"时先核对截图再动手**。

## 7. 存量清理工具（人工触发，不进每日流程）

| 工具 | 作用 | 默认行为 |
|---|---|---|
| `analyze_redundancy.py` | **多层次去冗余体检**（L0 硬重复 / L1 实体重复 / L2 标题套式 / L3 低信息量 / L4 主题同质），输出可执行工单 | 只报告；`--json` 写报告；`--gate` 用退出码表达结论 |
| `dedupe_deep.py` | 第二轮语义去重（同一事物的多个版本：改名仓库、arXiv+OpenAlex、媒体转载） | 只报告，`--apply` 才执行 |
| `prune_items.py` | 重要度分档（core/useful/noise），列出建议下架项 | **只报告**，`--apply` 才执行 |
| `scope_deep_read.py` | 把深读队列缩到可验证规模 | 改计划文件，`--restore` 还原 |

`analyze_redundancy.py` 与 `dedupe_deep.py` **已接入每日流程**（第 5 步，只报告），
`selfcheck` 也会断言其中的阈值。`prune_items.py` 保留为人工工具：**无人值守的夜间任务
不应该自动删除语料**。

### 7.1 去冗余为什么需要多种手段（实测结论）

| 层次 | 手段 | 实测结果（720 条语料） |
|---|---|---|
| L0 同一条内容被多处收录 | 稳定 id / 规范 URL / 标题指纹 / SimHash（采集器） + `dedupe_deep.py` | **0** —— 这一层已经做干净了 |
| L1 同一实体反复收录 | 罕见**专有名词** token | 面试×14、面经×13、微信×12、秋招×12 |
| L2 标题套式重复 | 规范化标题**前缀**重合 | 最高仅 ~3% |
| L3 低信息量占位 | 未分类 / 低于门槛 / 摘要过短 | **未分类 85 条（11.8%）**，其中 82 条同时低于相关度门槛 |
| L4 主题同质 | 分类内抽样两两 Jaccard | 最高 job 5%，其余 ≈0 |

**关键教训**：L2 最初用「分类内最高频 token 占比」，在中国语料上完全不可用 ——
中文没有词边界，bigram 会把 `算法工程师` 切成 `程师`、`法工`，每次加白名单只会产生
**下一个碎片**。最终改成「标题前缀重合」，不需要分词，结论也就不会随分词器漂移。
**一个输出由分词器决定的指标，比没有指标更糟。**

**三个都必须写 blocklist**：下架的条目记入
`state/collector-state.json` 的 `blockedIds` / `blockedTitleKeys`，
采集器在**导入阶段**和**索引重建阶段**各查一次。
少任何一道，下架的条目都会在下一轮复活 —— **这个坑真实发生过**（库从 554 反弹回 763）。

## 8. 审计工具（迁移时用来验收）

```bash
python scripts/audit_autonomy.py      # 自主性机制盘点：期望「0 缺失」
python scripts/audit_requirements.py  # 对原始需求逐条核对：期望 55/55
```

`audit_autonomy.py` 输出三类：`[已实现]` / `[需人工]` / `[缺失]`。
**迁移完成后必须是 0 缺失**；「需人工」是设计，不是缺陷。

## 9. 自检与迭代的完整闭环图

```
        ┌──────────────────────────────────────────────┐
        │  每日 18:00                                    │
        └───────────────────┬──────────────────────────┘
                            ↓
   采集 ──→ 自检 ──→ 配额规划 ──→ 深读(Agent) ──→ 关键词调优 ──→ 守卫 ──→ 发布
     │        │          │            │              │           │
     │        │          │            │              │           └ 门禁失败=拒绝发布
     │        │          │            │              └ 唯一自动生效（有护栏+审计日志）
     │        │          │            └ 产出提案（含可复核的条目 id）
     │        │          └ 质量闸门 + 每类配额 + backfill 队列
     │        └ 18 项断言；连续失败渠道升级告警；影响退出码
     └ 摘要回填 / 4 层去重 / blocklist 双检 / 每类入库上限
                            ↓
                  提案 & 审计日志（等人批）
                            ↓
        ┌──────────────────────────────────────────────┐
        │  你（人类）确认 → 下一轮生效                   │
        │  · keywordProposals：已自动，可回滚            │
        │  · taxonomy / channel / scoring：必须你批      │
        └──────────────────────────────────────────────┘
```
