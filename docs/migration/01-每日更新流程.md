# 01 · 每日更新流程（Pipeline）

> 目标：任何平台都能照这份文档重建每日流程，并知道**每一步失败时会发生什么**。
> 权威实现是 `scripts/run-daily.ps1`（Windows）。其它平台的等价物见第 6 节。

---

## 1. 触发与入口

> **架构变更（2026-10-02）**：触发方式已从 Windows 任务计划程序改为
> **DSH（Harness）自动化任务**，因为这样可以在一个专门的会话里观察每次更新的全过程。
> Windows 任务的**触发器已关闭**（任务变为 `Disabled`），但**任务定义完整保留**，
> 以便需要时重新启用或对照配置。**唯一自动触发入口是 Harness 自动化任务。**

| 项 | 值 |
|---|---|
| 计划时间 | **每日 18:00 Asia/Shanghai** |
| 承载 | **DSH 自动化任务**（`schedule-0c4e6ced…`），绑定到会话「工作台每日更新定时任务」 |
| 运行身份 | 与 DSH 应用相同的用户（非管理员） |
| 实际命令 | 在会话中执行 `$env:FUTURE_TRIGGER='scheduled'; & 'D:\pythonProject\DS-daily\scripts\run-daily.ps1'`，**不加任何 `-Skip*`** |
| 退出码 | `0` 正常 / `2` 部分渠道失败或自检有告警 / `1` 致命（采集本身失败） |
| 日志 | `web/data/logs/harness-YYYY-MM-DD.log`（UTF-8 无 BOM） |
| 重复触发保护 | `run-daily.ps1` 内置 **5 分钟新鲜度护栏**（数据刚刷新过则让路退出）；`-Force` 穿透 |
| 手动 / 排障入口 | **直接跑脚本**：`powershell -NoProfile -ExecutionPolicy Bypass -File scripts\run-daily.ps1 -Force` |

> ⚠️ **已禁用的计划任务无法用 `schtasks /Run` 启动** —— 会报
> `could not run because it is disabled`，即使 `AllowDemandStart=True` 也一样
> （该标志只表示"允许按需启动"，任务本身 `Disabled` 时仍然拒绝）。
> 要走 Task Scheduler 路径必须先 `Enable-ScheduledTask`。

## 2. 九个阶段（顺序不能变）

| # | 阶段 | 命令 | 失败后果 |
|---|---|---|---|
| 0 | 预检 | 检查 Python、`dsh`、LLM 凭据 | 缺 Python 直接退出；缺 `dsh`/凭据只跳过第 4 阶段 |
| 1 | **采集** | `python scripts/collect.py --trigger <t>` | **致命**（退出码 1）。数据不写 |
| 2 | **自检** | `python scripts/selfcheck.py` | 非致命但计入退出码 2 |
| 3 | **配额规划** | `python scripts/plan_deep_read.py --all` | 非致命；Agent 将没有工作清单 |
| 4 | **深读（LLM）** | `dsh headless --json -` 读 `scripts/daily-agent.md` | **非致命**，退出码不变。数据层不受影响 |
| 5 | **关键词自动调优** | `python scripts/tune_keywords.py` | 非致命；关键词保持原样 |
| 6 | **产物守卫** | `python scripts/run_guards.py` | 公式门禁失败 → **拒绝发布**（见下） |
| 7 | 构建站点 | `python scripts/build_site.py` | 非致命 |
| 8 | 发布 | `powershell scripts/publish-workbuddy.ps1` + WorkBuddy 上传 `dist/` | 非致命；本地 dist/ 不受影响 |
| 9 | 收尾 | `selfcheck --summary` + 写退出码 | — |

**为什么第 1 阶段之后一切都"非致命"**：一次网络抖动不应该让当天的数据白采。
除了采集本身失败，任何环节出错都只写日志，数据该落盘的照常落盘。

**第 6 阶段的门禁逻辑**（重要）：
```
公式渲染失败 → 说明有畸形 LaTeX → 会让「公式剖析」整页空白
             → 于是 siteOk = false → 跳过发布
             → 保留线上昨天那份正常站点（宁可旧，不可坏）
```

## 3. 每个阶段的输入 / 输出

### 3.1 `collect.py`（确定性层，无 LLM）

```
输入：config/collector.config.json, research/source_registry.json
      web/data/inbox/*（人工导入，可选）
      web/data/feedback.json（学习信号，可选）
      web/data/state/collector-state.json（去重指纹 + blocklist）
输出：web/data/items/index.json      ← 全量知识卡片（唯一真相）
      web/data/items.json            ← 同一份数据的本地副本
      web/data/digest/YYYY-MM-DD.json + today.json
      web/data/manifest.json         ← 本轮摘要 + schedule + health
      web/data/sources.json          ← 渠道清单与实测状态
      web/data/logs/runs.json        ← 运行历史（append，保留最近 120 条）
      web/data/proposals/YYYY-MM-DD.json + latest.json
      web/data/state/collector-state.json（私有）
```

内部顺序：**采集 → 摘要回填 → blocklist 过滤 → 相关度门槛 → 分类 → 打分 →
学习信号加分 → blocklist 再滤 → 去重合并 → 每类入库上限 → 原子写入**。

> ⚠️ **blocklist 检查了两遍**（导入阶段 + 索引重建阶段）。少任何一遍，被下架的条目
> 都会在下一轮复活 —— 这个坑真实发生过（库从 554 反弹回 763）。

常用参数：
```bash
python scripts/collect.py                  # 正常全量
python scripts/collect.py --trigger scheduled
python scripts/collect.py --only arxiv,hf_papers --limit 10 -v   # 调试（隐含 --narrow）
python scripts/collect.py --narrow         # 部分渠道跑，但不缩减当天 digest
python scripts/collect.py --dry-run        # 不写盘
python scripts/collect.py --probe          # 只探渠道健康，不写数据
python scripts/collect.py --rescore        # 改完关键词/权重后重算全库分类与分数
python scripts/collect.py --init-config    # 写配置模板
python scripts/collect.py --no-enrich      # 跳过摘要回填（快，但会留标题党卡片）
python scripts/collect.py --kb-backfill 60  # 一次性：每个算法知识库多取 60 页，清存量
```

### 3.1.1 算法知识库渠道（`knowledgeBase`）

`programmercarl` / `kamacoder_notes` / `gh_algokb` 三个渠道与其它渠道的采法**不同**：

```
sitemap.xml  →  按 family 分组 → 组间轮转（避免单轮全是一个分类）
             →  取当日窗口（默认 15 页/渠道）→ 抓每页真实 <h1>/<title> + meta description
             →  打上该 family 的 tags（tags 参与分类）→ 交给统一的 normalize/打分/去重
```

| 为什么这么设计 | 说明 |
|---|---|
| 用 sitemap 而不是 feed | 题解/八股是**参考资料**，不是新闻；站点没有"最新"这个维度 |
| 按天轮转 | 414+283 页的库约一个月吃透，不强求一次性抓完（`--kb-backfill` 可加速） |
| `knowledgeBase=True` | `score_item` 多一个**与日期无关**的分量；`perCategoryPerRun` 不再裁剪它 |
| family 之间轮转 | 否则一个窗口可能全是 `/go/` 八股，触发「标题套式重复」告警 |
| suffix 不能是别类的关键词 | 标题命中权重是正文的 3 倍，一个 `知识点` 后缀就能把 `posttraining` 内容拽进 `exam` |

### 3.3 `plan_deep_read.py`

输出 `web/data/deep-read-plan.json`，含**两个清单**：

| 键 | 含义 |
|---|---|
| `queue` | **尚未深读**的条目（已过质量闸门 + 每类 2–10 条配额） |
| `backfill` | **已深读但解析不完整**的条目，带 `missing: ["diagram","formulas","teaching"]` |
| `skimmed` / `skimByRule` | 被质量闸门挡掉的条目与原因（可审计） |
| `perCategory` | 每个分类的名额、候选数、权重 |

```bash
python scripts/plan_deep_read.py --all        # 每日流程用这个
python scripts/plan_deep_read.py --fresh-only # 只看当天新增
python scripts/plan_deep_read.py --show       # 打印清单
```

**平台无关**：任何能读写文件、能跑 Python 的 agent 都可以执行。

### 3.5 `run_guards.py`

| 守卫 | 性质 | 失败含义 |
|---|---|---|
| `check-formulas.mjs` | **门禁**（阻断发布） | 有 LaTeX 会让渲染器抛异常 → 公式页整页空白 |
| `tex-audit.mjs` | **门禁**（阻断发布） | 渲染器不认识的命令会降级显示原始 LaTeX（如 `\!`、`\odot`）→ 读者看到"数学没渲染" |
| `audit-layout.mjs` | 体检（仅记录） | 有内容被 `overflow` **真正裁掉**（不隐藏溢出的元素不报） |
| `verify-text-stacking.mjs` | 体检（仅记录） | 短标签被 `grid` 布局逐字竖排 |
| `verify-collapse.mjs` | 体检（仅记录） | 折叠控件点击后界面无变化 |

```bash
python scripts/run_guards.py                # 全跑（自带静态服务器，无需外部服务）
python scripts/run_guards.py --skip-layout  # 只跑两个公式门禁（快）
node scripts/tex-audit.mjs --verbose        # 单独看是哪几条公式泄漏了哪个命令
```

> ⚠️ 布局审计**只报告真正被裁掉的内容**：① `overflow` 不隐藏的元素不算（内容会画出来）；
> ② 短标签（≤6 字符）不算；③ 有滚动祖先的元素不算。加这三条过滤之前，它每次报 130+ 项，
> 其中绝大多数是 3 个字符的时间戳 —— **一个永远失败的守卫等于没有守卫**。

### 3.6 ~ 3.8 构建与发布

```bash
python scripts/build_site.py                                    # dist/ + 隐私审计
powershell -File scripts/publish-workbuddy.ps1                  # 审计 + 交接发布请求
powershell -File scripts/publish-workbuddy.ps1 -SkipAudit       # 跳过审计（仅调试）
```
`build_site.py` 用**白名单**复制并断言：`state/`、`inbox/`、`harness-*.log`、
`*.part.js`、`items.json`、`feedback.json` 都不进 `dist/`。

`publish-workbuddy.ps1` 在此之上**独立再做一次**隐私审计（不通过就不交接任何内容），
然后打印一行机器可读的请求，供每日自动化上传：

```
[WORKBUDDY-PUBLISH] directory=<abs dist path> status=ready
```

**发布是平台动作，不是一个 shell 命令。** WorkBuddy 按「目录」绑定应用，同一目录重复
发布**覆盖同一条稳定链接**，所以不需要把 URL 写进任何文件。脚本负责确定性的那一半
（校验 + 审计 + 交接），上传由自动化紧接着执行（见第 6 节移植说明）。

## 3.9 采集量的控制（质量优先，宁少勿滥）

**这是最容易调错、也最影响长期可用性的一组参数。** 实测教训：一次运行的
`maxNewPerRun=400` + arXiv 10 天回溯，让单轮入库 **190+ 条**，语料从 550 涨到 720；
这些条目里 99.7% 都通过了 `minRelevance=12` 的门槛，也就是说**门槛根本没在过滤**。

根因：打分公式里 `sourceTierWeight` 会整体放大 P0 渠道（arXiv / GitHub / HF）的分数，
使全库相关度被压缩在 49–62 的窄带里（p25=49.6，median=56.2，p75=62.0）。
**结论：单靠相关度门槛无法控制采集量，必须有硬上限。**

当前设置（`config/collector.config.json`）：

| 键 | 值 | 作用 |
|---|---|---|
| `limits.perChannel` | 12 | 单渠道单轮上限。arXiv 曾单轮贡献 235 条 |
| `limits.maxNewPerRun` | 60 | 单轮新增总量上限 |
| `limits.perCategoryPerRun` | 8 | 单类单轮上限，贴近「每方向 2–10 条深读」的节奏 |
| `scoring.minRelevance` | 45 | 实测 45 分仍保留 79% 的已分类条目，所以不算激进；它主要剔除明显无关的长尾（firebase-ios-sdk、cursor 插件、GhostTrack） |
| `arxiv.lookbackDays` | 3 | 原为 10，等于每天重新扫一遍同一批积压 |
| `arxiv.maxPerQuery` | 10 | 原为 25 |
| `github.minStars` | 120 | 原为 40，玩具仓库太多 |
| `github.lookbackDays` | 7 | 原为 30 |
| `limits.dropUnclassified` | true | 无关键词命中的条目**不入库**（详见下） |
| `interests` | 见配置 | **动态调整各方向比重**的旋钮 |
| `categoryIntakeWeight` | 见配置 | 每类名额权重，让"面经/算法题"拿到更多位置 |
| `channelIntakeOverride` | 见配置 | 单渠道名额覆盖（稀缺但高价值的源例外） |

### 3.10 内容配比：怎么"动态调整面经/算法题/领域知识/岗位技能"的比重

**旋钮是 `interests`**（不是代码）：`classify()` 用 `权重 × interests[类目]` 给每个类目打分，
所以提高某个值会同时把它**排上来**并**提高其单轮入库占比**。

实测问题：`job` / `coding` / `exam` / `paper` / `course` 原本**根本不在 `interests` 里**，
于是算法题与面经内容拿的是 0.8 的默认值，而研究类目拿 1.0 —— 与"求职工作台"的定位相反。

现在的配比（数值即相对比重）：

| 类目 | interests | 说明 |
|---|---|---|
| `coding` | 1.35 | 手撕题、算法题、面经（题库定位页） |
| `job` | 1.30 | 正式岗位、技能要求 |
| `exam` | 1.20 | 笔试、八股 |
| `multimodal` / `posttraining` | 1.10 | 四个目标方向 |
| `worldmodel` | 1.05 | |
| `rl` | 1.00 | |
| `generative` / `agent` / `engineering` | 0.80–0.85 | 支撑方向 |
| `foundation` | 0.75 | |
| `course` / `paper` | 0.55–0.60 | 降权：泛论文列表与课程广告 |
| `trend` | 0.45 | **读者明确不要无关新闻** |
| `unclassified` | 0.00 | 另有一道硬闸门 |

**为什么面经要更高**：面经是这套工作台里**时效性最强**的内容 —— 2024 年的面经对 2026 年的投递
几乎没有参考价值。所以它既要在排序上靠前，又要在名额上更多，还要在**展示上按时间倒序**
（见 `docs/migration/02-数据契约.md` 的 `interview.json`）。

`categoryIntakeWeight` 把这份配比**落到单轮名额**上：`coding` 拿到 1.8 倍名额、`trend` 只有 0.4 倍。
**光靠权重不够** —— 权重只影响排序，名额才决定"这一天到底收进来多少面经"。

### 3.11 未分类卡片不入库（两道闸门）

| 位置 | 行为 |
|---|---|
| 采集阶段 | `category == "unclassified"` 直接丢弃并单独计数（日志里的 `unclassified=N`） |
| 索引重建 | `build_all_items()` 再过滤一次，保证历史存量也不会出现在发布语料里 |

**但 `state["canonical"]` 里保留它们**。这是刻意的：如果以后关键词改进了，
`--rescore` 会重新分类存下来的条目，其中真的有价值的会自动回到库里。
代价只是几百 KB，换来的是"不可逆决定"的保险。

> 实测：一次 rescore 就把 **35 条**未分类条目重新归入了正确的方向。

调参方法论（照做即可）：
```bash
# 1. 看清当前分布，别凭感觉
python -c "import json;d=json.load(open('web/data/items/index.json',encoding='utf-8'));\
r=sorted(float(i.get('relevanceScore') or 0) for i in d['items']);n=len(r);\
print('min',r[0],'p25',r[n//4],'median',r[n//2],'p75',r[3*n//4])"

# 2. 试算某个门槛会保留多少
#    （阈值选择依据：想让保留率落在 70–90% 之间，太高说明门槛无效）

# 3. 改完必须重新打分，否则新阈值对存量条目不生效
python scripts/collect.py --rescore
```

> ⚠️ **`--rescore` 也会重新生成 `taxonomy.json`。** 这一点曾经是 bug：
> 分类法只在完整采集路径里写，于是新增分类后跑一次 rescore，就会出现
> 「条目用了分类 X，但 taxonomy 里没有 X」，selfcheck 报 85 条警告 —— 真警告被淹没。

## 5. 失败语义一览（迁移时最需要照搬的部分）

| 失败 | 会发生什么 | 你该做什么 |
|---|---|---|
| 某渠道超时/403 | 该渠道记 `status=blocked/error`，其它渠道照常 | 看 `sources.json.riskNote`；连续 3 轮失败会进提案 |
| 单个渠道解析失败 | 只影响该渠道（`status=parse_error`） | 这是**我们**的问题（响应格式变了），需改解析 |
| arXiv 挂 | 该渠道空，其它继续；`status=partial` | 无需处理，明天会自己重试 |
| LLM 不可用/无凭据 | 第 4 阶段跳过，**数据照常**，卡片显示「仅摘要」 | 配好凭据；不影响采集 |
| 深读层写坏 JSON | `selfcheck` 报错，退出码 2 | 跑 `verify_web_data.py` 定位 |
| 公式门禁失败 | **拒绝发布**，线上保留旧站点 | 修 `formulas.json` 里那条 LaTeX |
| 网络断（发布失败） | 本地数据已更新，站点停在上次版本 | 恢复网络后重跑发布 |
| 磁盘满 / 写盘失败 | 原子写（`os.replace`）保证不写坏旧文件 | 清空间后重跑 |

## 6. 移植到非 Windows 平台

需要替换的**只有第 0 阶段与第 8 阶段的调度与发布**。等价做法：

**cron（Linux/macOS）**
```cron
# 18:00 Asia/Shanghai —— 注意容器/服务器时区，或显式用 TZ
TZ=Asia/Shanghai
0 18 * * * cd /path/to/workbench && FUTURE_TRIGGER=scheduled ./run-daily.sh >> logs/cron.log 2>&1
```

`run-daily.sh` 的等价骨架（与 PowerShell 版逐阶段对应）：
```bash
#!/usr/bin/env bash
set -uo pipefail            # 注意：不用 -e，除采集外都要"失败继续"
cd "$(dirname "$0")/.."
PY=python3
export FUTURE_TRIGGER="${FUTURE_TRIGGER:-manual}"

$PY scripts/collect.py --trigger "$FUTURE_TRIGGER" || exit 1     # 1 采集（致命）

$PY scripts/selfcheck.py;            CHECK=$?                     # 2 自检
$PY scripts/plan_deep_read.py --all                               # 3 配额
# 4 深读：换成你的平台（Claude Code / API 调用 / ...）
#   把 scripts/daily-agent.md 的内容作为提示词，工作目录设为本仓库根
your-agent-cli run --prompt-file scripts/daily-agent.md || true
$PY scripts/tune_keywords.py                                      # 5 自调优

GUARD=0; $PY scripts/run_guards.py || GUARD=1                     # 6 守卫

if [ "$GUARD" -eq 0 ]; then                                        # 7+8 构建与发布
  $PY scripts/build_site.py && ./scripts/publish-workbuddy.sh      # 审计 + 交接
  your-agent-cli publish-dir dist                                  # 平台动作：上传 dist/
else
  echo "guard failed: publish held back" >&2
fi

$PY scripts/selfcheck.py --summary                                 # 9 收尾
[ "${CHECK:-0}" -ne 0 ] && exit 2 || exit 0
```

**发布层**：本工作台不再提交、不再推送，也没有 `gh-pages` 分支与 `*.github.io`
地址。`publish-workbuddy.ps1` 只做「校验 + 独立隐私审计 + 打印发布请求」，真正的
上传是一个**平台动作**（WorkBuddy 按目录绑定应用，同一目录重复发布覆盖同一条稳定
链接）。因此在别的平台迁移时，只要把这一步换成该平台的等价物即可：
`rsync` 到服务器、对象存储上传（S3/OSS）、Vercel/Netlify 的 CLI，或任何
「把 `dist/` 目录发布成一个站点」的工具。**关键约束**：审计必须在每次发布前跑，
且发布失败不得影响本地数据刷新。

> 如果目标平台就是 git 系（GitHub Pages / GitLab Pages），注意**不要用
> `git subtree push --prefix dist`** —— `dist/` 被 `.gitignore` 排除，不是任何
> commit 里的已跟踪路径，必然报 `fatal: 'dist' does not exist; use 'git subtree add'`。

### 6.1 环境依赖（极少，故意的）

| 依赖 | 版本 | 用途 | 必需？ |
|---|---|---|---|
| Python | ≥ 3.8 | 采集、自检、规划、构建 | **必需**，且**只用标准库** |
| Node.js | ≥ 18 | 前端拼接、语法校验、无头浏览器校验 | 改前端/跑守卫时必需 |
| Chrome/Edge | 任意近期 | `verify-web.mjs`、`audit-layout.mjs` | 仅这两项需要 |
| git | 任意 | 本地版本控制（**发布不再依赖它**） | 否 |
| LLM CLI/API | — | 第 4 阶段深读 | 可选；没有就只出「仅摘要」 |

**没有 `requirements.txt`、没有 `package.json`、没有 `node_modules`。**
这是刻意的：迁移到任何机器都不需要联网装依赖。

## 7. 一次典型运行的耗时（实测，用于容量规划）

| 阶段 | 实测耗时 |
|---|---|
| 采集（15 渠道 + 摘要回填） | ~190–280 s |
| 自检 | ~2 s |
| 配额规划 | ~3 s |
| 深读（13 条 + 17 公式） | **~450 s** |
| 关键词调优 | < 1 s |
| 守卫（含布局审计） | ~60–180 s |
| 构建 + 发布 | ~40 s |
| **合计** | **约 13–22 分钟**（只跑采集层约 5 分钟） |

> Windows 任务计划程序（现处于 `Disabled`）保留了 `ExecutionTimeLimit=PT3H`，
> 用来防止某个渠道卡死导致任务永远挂着。**Harness 自动化没有这个上限**，
> 所以如果改回 Task Scheduler，务必保留该设置；若继续用 Harness 自动化，
> 需要靠脚本自身的渠道超时（`config` 里的 `http.defaultTimeout` 与重试配置）兜底。
