# Future · 求职学习工作台 — 信息架构与数据契约

> 本文回答三件事：**每天采什么**、**怎么去重与归纳**、**怎么稳定地存下来并给网页用**。
> 它同时是采集器（`scripts/collect.py`）、Agent 深读层（`scripts/daily-agent.md`）与
> 网页数据层（`web/data/`）之间的契约。任何一方要改字段，先改这里。

- 目标画像：AI 专业在读硕士，约 6 个月后投递**算法实习**
- 方向：多模态算法 / Post-training 后训练 / 生成式模型 / 世界模型（并可扩展到 RL、Agent、具身）
- 更新频率：每日 18:00 (Asia/Shanghai)，Windows 任务计划程序触发
- 技术约束：采集器**只用 Python 标准库**；网页**零依赖、零构建**（`file://` 直接可开）

## 一、任务分析与信息架构

### 1.1 每日调研要解决的真实问题

求职期的信息需求不是"读得多"，而是四件事同时成立：

| 需求 | 如果缺失会怎样 | 本文档中的对应设计 |
|---|---|---|
| **不漏** | 错过某个厂的开窗期，半年后才发现 | 渠道分层 + 每日 18:00 + 岗位看板 + 招聘节奏字段 |
| **不重** | 同一篇论文在 arXiv/HF/公众号出现三次，噪音淹没信号 | 四层去重（ID / URL / 标题 / SimHash）+ `mergedFrom` 合并 |
| **可判断** | 收藏 500 条，面试前不知道看哪条 | 相关度打分 + `why`（为什么重要）+ 难度 + 掌握度标记 |
| **能转化** | 看过 ≠ 会讲，面试时说不清 | 公式剖析（符号→推导→类比→代码→易错点）、题库定位、学习路线与验收标准 |

### 1.3 采集渠道与优先级

优先级决定时间预算、打分权重（P0 = 1.0 / P1 = 0.85 / P2 = 0.7）与失败语义。

**P0 — 必须有，失败要告警**

| 渠道 | 模式 | 说明 |
|---|---|---|
| `arxiv` | API (Atom) | 按分类关键词构造 OR 查询，按提交时间倒序，回溯 10 天 |
| `hf_papers` | API | HuggingFace Daily Papers，社区热度作为质量信号 |
| `github` | API | 按主题 + star 阈值 + 最近推送搜索，带 `GITHUB_TOKEN` 可提速 |
| `openreview` | API | 顶会投稿与评审；`/notes` 被 Cloudflare 挑战时退避重试 |
| `jobs_bytedance` / `jobs_tencent` | API | 腾讯 `careers.tencent.com` 有免登录 JSON；字节接口为 POST |
| `leetcode` | API | 公开题库接口（GraphQL 被挑战时用 legacy 接口） |

**P1 — 有价值，失败降级**

`hf_models`、`gh_trending`、`semantic-scholar`、`hn`、`qbitai`、`machineheart`、
`nowcoder`、`jobs_alibaba`、`openalex`、`crossref`、`acl-anthology`、实验室博客
（OpenAI / DeepMind / GoogleAI / MSR / NVIDIA / Anthropic）

**P2 — 可选，默认不跑**

`reddit`、`rsshub`（公共实例被 Cloudflare 拦）、`paperswithcode`（已下线）、
`alphaXiv`、36氪、各厂招聘 SPA（字节/智谱/月之暗面/DeepSeek/MiniMax/上海AI Lab）、AtCoder

**MANUAL — 禁止自动抓取，必须人工登录后导入**

`小红书`、`BOSS直聘`、`拉勾`、`实习僧`、`猎聘`、`脉脉`。
其中 BOSS直聘的 `robots.txt` 明确 `Disallow: /*?query=*`（正好是搜索 URL），
小红书 robots 全站 `Disallow: /`，Reddit JSON 也是 `Disallow: /`。

详见 `research/source_registry.json`（91 个渠道，含实测 HTTP 状态码与 robots 原文证据）
与 `research/channel_probe.json`（本机探针结果）。

### 1.4 需要登录的渠道：人工在环流程

自动抓取登录站点会违反服务条款，也会导致账号风控。因此设计为**人工在环**：

1. 你按自己的节奏登录小红书 / BOSS直聘，把感兴趣的岗位或帖子导出为 CSV 或手工整理成 JSON；
2. 放到 `web/data/inbox/`（支持 `manual.jsonl`、`*.csv`、`*.json`）；
3. 下次采集运行时读取本地文件合入知识库，**对这些站点的网络请求数为 0**；
4. 作品台「采集与运行」页会显示这些渠道为 `manual`，并提示待导入数量。

账号密码**永远不需要**提供给我或写进任何文件。

## 二、去重与更新规则

### 2.1 四层去重（由便宜到昂贵，命中即停）

| 层 | 规则 | 目的 |
|---|---|---|
| L1 稳定 ID | `id = sha1(sourceId + "::" + externalId)[:16]` | 同源同条目的精确命中 |
| L2 规范化 URL | 剥离 20+ 追踪参数（`utm_*`/`spm`/`share_*`/`ref`…），host 去掉 `www.`，路径去尾斜杠，**arXiv 去 `vN`** | 跨渠道同一资源 |
| L3 标题指纹 | 去空白/标点/大小写后 `sha1` | 转载、不同渠道同一标题 |
| L4 SimHash | 64 位，中文按字 3-gram、英文按词 3-gram；汉明距离 ≤ 3 判重 | 近似重复（改写标题、摘要雷同） |

命中 L2/L3/L4 时**不是丢弃**，而是 `merge_duplicate()`：保留更长摘要、合并
`authors/tags/sources`、质量信号取最大值、记录 `mergedFrom[]`。
这样"arXiv 论文 + HF Daily + 媒体报道"会合并成一条卡片，但三个来源链接都在。

### 2.2 更新规则（增量，不破坏用户状态）

| 情况 | 动作 |
|---|---|
| 首次出现 | 新建卡片，写 `firstSeen`，`learning.status = "unread"` |
| 已存在且 `contentHash` 变化 | 更新 `title/summary/qualitySignals`，**保留 `learning` 与 `firstSeen`** |
| 已存在且内容未变 | 只更新 `lastSeen`，不计入"新增"，不重复展示 |
| 90 天未再命中且未被收藏 | 归档到 `archive/`（由 `retention.archiveAfterDays` 控制） |

### 2.3 相关度打分（可复现，系数全部显式）

```
relevanceScore = clamp( round( (
      0.40 × category   +   // 分类关键词命中：标题命中 3 分/词，正文 1 分/词，上限 40
      0.30 × freshness  +   // 时效：30 × 0.5^(age_days / halfLife)，halfLife 默认 7 天
      0.12 × source     +   // 来源层级：P0=1.0, P1=0.85, P2=0.7
      0.18 × quality    +   // 同行评审 +8、stars^0.5×0.8、upvotes^0.65/2、有代码 +2，上限 17.6
      0.09 × content        // 摘要完整度：每 220 字符 9 分，上限 9
) × zhBonus ), 0, 100 )
```
`zhBonus = 1.04`（中文来源对国内求职更实用）。`minRelevance = 12` 以下的条目直接丢弃。

排序 tie-breaker：相关度 → 发布时间倒序 → `id` 字典序（**保证同一份数据每次渲染顺序一致**）。

### 2.4 归纳与结构化存储

分两层，职责不重叠：

- **确定性层（`collect.py`）**：只做规范化与机械摘要。`why` 字段由**观察到的信号**拼装
  （命中的关键词、是否同行评审、star 数、社区热度、是否有开源实现、是否中文来源），
  **不做任何事实推断**。摘要只取原文 `abstract` / `description`，缺摘要就留空并计入
  `selfcheck` 的"空摘要率"。
- **归纳层（`daily-agent.md`，可选）**：对相关度最高的 8–12 条做深读，产出
  `tldr / keyPoints / concepts / formulas / selfCheck`。概念必须包含：
  **一句话结论 → 背景 → 机制 → 生活类比（含失效边界）→ 公式逐符号拆解 → 可视化方案
  → 前置知识 → 自测题**。每条断言必须能追溯到原文 `summary`，无法确认的写进
  `selfCheck.uncertain`。

```
├─ digest/
│  ├─ YYYY-MM-DD.json          # 当日增量（含 run 记录与分类统计）

├─ taxonomy.json               # 分类体系（名称/目标/节奏/关键词）

├─ jobs.json                   # 岗位库（人工整理 + 每日增量）
├─ learning.json               # 学习路线/论文/仓库/课程/里程碑/学习系统
├─ formulas.json               # 公式剖析库（种子 + 每日新增，按 id 去重合并）
├─ enrichment.json             # Agent 深读产物，byId 索引
├─ proposals/YYYY-MM-DD.json   # 自我迭代提案（只建议，不自动生效）
├─ logs/
│  ├─ runs.json                # 最近 120 次运行记录
│  ├─ harness-YYYY-MM-DD.log   # 运行日志
│  └─ agent-YYYY-MM-DD.json    # Agent 层运行记录
├─ inbox/                      # 人工导入的登录类渠道数据
└─ state/collector-state.json  # 去重指纹、firstSeen/lastSeen、渠道健康
```

### 3.2 `knowledge-item` 契约（前端唯一依赖的字段集）

```jsonc
{
  "id": "a1b2c3d4e5f60718",        // sha1(source::external)[:16]，稳定主键
  "sourceId": "arxiv",              // 渠道 id
  "channel": "arxiv",
  "externalId": "2509.12345",       // 源站 id（arXiv 去掉 vN）
  "category": "posttraining",       // 必须是 taxonomy 中的 id
  "title": "…",
  "summary": "…",                   // 来自原文，禁止编造
  "why": "归属「后训练」方向；命中关键词 dpo、preference optimization；…",
  "url": "https://arxiv.org/abs/2509.12345",
  "canonicalUrl": "https://arxiv.org/abs/2509.12345",
  "sources": [{ "url": "…", "name": "arxiv" }],
  "authors": ["…"],
  "publishedAt": "2026-09-30T20:00:00+08:00",
  "fetchedAt": "2026-10-01T20:00:12+08:00",
  "lang": "en",
  "tags": ["cs.CL", "…"],
  "difficulty": null,
  "relevanceScore": 78.4,
  "relevanceBreakdown": { "category": 24.0, "freshness": 28.1, "…": 0 },
  "qualitySignals": { "upvotes": 42, "codeAvailable": true },
  "peerReviewed": false,
  "codeAvailable": true,
  "venue": "arXiv",
  "ccf": null,
  "stars": null,
  "firstSeen": "2026-10-01",
  "lastSeen": "2026-10-01",
  "contentHash": "9f8e7d6c5b4a3210",
  "date": "2026-10-01"               // = firstSeen 的日期部分，前端按天分组用
}
```

**用户的阅读状态（收藏 / 学习中 / 已掌握 / 笔记 / 掌握度 / 任务勾选 / 投递阶段）
全部存在浏览器 `localStorage`**，不写回数据层。理由：这些是"我的"数据，与"采集"数据
生命周期不同；一旦混在一起，重新采集就有覆盖风险。`localStorage` 可一键导出为 JSON
（顶栏「导出进度」），换设备时导入即可。

### 3.3 写入协议（为什么这样写）

- **原子写**：写临时文件 `name.<pid>.tmp` + `os.replace()`，读到的永远是完整的旧版或新版，
  不会出现半截 JSON。占位检查：小于 2 字节视为可疑，拒绝替换。
- **UTF-8 无 BOM**：`json.dump(..., ensure_ascii=False)` 直接写；BOM 会让浏览器 JSON 解析
  和 `node --check` 都失败。
- **幂等**：重复运行同一天，`state` 里的指纹会让第二次只新增真正的新条目。实测第二次运行
  `new=1, updated=525, duplicate_hits=525`。
- **失败域隔离**：单渠道异常被 `ThreadPoolExecutor` 的 future 捕获，写入该渠道
  `status: error/empty` 后继续；整轮结果标记 `ok / partial / error`。

## 四、可靠性工程

| 机制 | 参数 | 位置 |
|---|---|---|
| 重试 | 每个 GET 最多 `retries + 1` 次，指数退避 `base^(n) + jitter`，base=1.6，jitter=0.35 | `http_get()` |
| 可重试状态码 | 403 / 408 / 425 / 429 / 500 / 502 / 503 / 504 | `http_get()` |
| 渠道超时 | P0/P1 = 30s，P2 = 20–25s（按渠道单独配置） | `CHANNEL_SPECS` |
| 渠道并发 | 最多 6 线程；同一 host 有最小间隔（GitHub 未授权 6.5s） | `run()` |
| 备用来源 | 每渠道 `backup: [...]` 字段声明替代源；采集器按序尝试 | `CHANNEL_SPECS` |
| 熔断 | 同一渠道连续 3 次 `error/blocked` → 写入告警并进入人工复核（`proposals/`） | `selfcheck.py` |
| 任务层重试 | 任务计划程序 `RestartOnFailure 20min × 2`，`StartWhenAvailable` 补跑 | 任务 XML |
| 部分失败语义 | 单渠道失败绝不终止整轮；`status=partial` 仍会写数据 | `run()` |
| 配额自适应 | `GITHUB_TOKEN` 存在时缩短间隔；未授权时降到 10 次/分钟以下 | `collect_github()` |

### 日志与状态回写

- `logs/runs.json`：每轮一条 `{startedAt, finishedAt, status, durationSec, channelsOk,
  channelsTotal, newItems, updatedItems, duplicates, rawItems, itemsFile, notes}`，
  保留 120 条。`notes` 里逐渠道记录非 `ok` 状态，这正是"连续失败"告警的输入。
- `logs/harness-YYYY-MM-DD.log`：任务层日志（含 Agent 层的完整输出）。
- `state/collector-state.json`：`byKey/byUrl/byTitle` 指纹表（各上限 6 万条）、
  `hashes`（SimHash，上限 4 万条）、`firstSeen/lastSeen`、`seenIds`。
- `manifest.json`：给网页的汇总（`lastRunAt / channelsOk / newItems / totalItems / status`）。

### 告警条件（`selfcheck.py` 实现）

| 条件 | 级别 |
|---|---|
| 有 JSON 文件解析失败 / 必需产物缺失 / 条目无来源 URL / 条目无分类 / id 重复 | **错误**（exit 1） |
| manifest 与索引数量不一致 / digest 出现孤儿条目 / 空摘要率 > 20% / 未知域名占比 > 15% | 警告（exit 2） |
| 距上次成功运行 > 36 小时 / 某渠道连续 3 轮失败 | 警告 |
| 分类覆盖为空（如 `coding` 暂无数据） | 提示 |

## 五、真实性与准确性自查

这是本工作台最容易被稀释、也最必须守住的部分。

1. **来源强制**：没有 URL 的条目在 `normalize()` 阶段直接丢弃（`selfcheck` 会再验一次）。
2. **禁止推断**：确定性层的摘要只来自原文；`why` 只由观察到的信号拼装。Agent 层的每条
   断言必须能追溯到输入条目的 `summary`，无法确认的进 `selfCheck.uncertain`。
3. **数字标注可信度**：薪资、名额、截止时间等一律带 `confidence`；媒体转述的"天花板"
   数字（如某些日薪最高值）标 `low` 并注明"极少数、不可当预期"。
4. **自动/人工分区**：`sources[].name` 标明来源渠道，界面逐个展示，人工整理与自动采集
   的内容在视觉上可区分。
5. **每日抽检**：`selfcheck.py` 检查空摘要率、未知域名占比、重复率、分类覆盖率；
   `scripts/probe-channels.py` 可随时重测渠道可达性并留档证据（`research/_probe/`）。
6. **不美化**：渠道失败就显示失败。`status=partial` 与失败渠道列表直接呈现在
   「采集与运行」页，不做"看起来一切正常"的假象。

## 六、抽象概念易读化与可视化设计

抽象概念是求职面试的主要失分点，因此每个概念固定八层结构（Agent 层产出，
网页「公式剖析」与知识详情页渲染）：

1. **一句话结论** —— 它到底做了什么
2. **背景与问题** —— 没有它之前人们怎么做，卡在哪
3. **机制** —— 关键设计选择与它解决了什么
4. **生活类比** —— 必须具体到可想象，且注明**类比在什么地方失效**
5. **公式逐符号拆解** —— 符号表 + 每个符号的量纲/shape + 出处
6. **可视化方案** —— 画什么轴、什么形状、什么颜色代表什么（用文字描述，不依赖图片）
7. **前置知识与术语** —— 读它之前需要会什么
8. **自测题** —— 3 道，能答对才算学会

网页端的实现：公式卡片按「符号表 → 推导链条 → 生活类比 → 可运行代码 → 易错点」展开，
`<details>` 折叠降低信息密度，代码块带复制按钮。类比用高亮框与公式区分离，避免
把"直觉"误当成"结论"。

## 七、自我迭代机制

```
observe（采集器记录命中率、噪声率、渠道健康、用户未点击/未收藏的条目）
   ↓
propose（Agent 写 web/data/proposals/YYYY-MM-DD.json）
   ↓
review（人工在「采集与运行」页查看，逐条确认）
   ↓
apply（只把确认过的改动写回 config/collector.config.json 或 CHANNEL_SPECS）
   ↓
measure（下一轮 related 指标对比：相关度分布、分类覆盖率、人工点击率）
```

**自动生效的只有**：单个关键词权重的微调（≤10%）。
**必须人工确认的**：分类增删改名、渠道增删与升降级、评分公式与权重、去重阈值、
blocklist、任何 `robots.txt` 状态变化。
